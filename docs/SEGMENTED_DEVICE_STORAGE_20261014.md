# Immutable Android physical ledger segments — batch22

The logical Market Paper v1 JSON and CAS comparison remain byte-for-byte unchanged. The Android physical file becomes a small `paper-segment-manifest-v1` root referencing immutable SHA-256 chunks under its app-private `.segments` directory. Content-defined32–128KiB boundaries resynchronize after small insertions/appends, so unchanged archive bytes can be reused despite a cash/account prefix changing length. Boundary hashes are not security checks; every chunk and the reassembled original ledger have SHA-256 verification.

Ordering: enforce current logical-byte CAS → preserve the original legacy ledger as a permanent verified manifest → stage new immutable chunks with file fsync → directory fsync → AtomicFile root commit → parent-directory fsync → exact uncached logical readback → initialized marker. A post-publication durability/readback error latches that native path unavailable until process restart; the Dart controller cannot turn an ambiguous write into an approved fill using cached preferences. No existing ledger/history is deleted, no garbage collector runs, and interrupted staging cannot replace the prior published root. Missing/tampered/reordered/traversal references fail closed, never reconstruct an empty ledger. Unknown physical formats are rejected.

New JVM acceptance exercises exact Arabic UTF-8, unchanged chunk reuse under prefix insertion+append, failed directory sync before root publication, missing/corrupt chunks, manifest length/digest/order/path/type tampering, retained legacy anchors, limits/invalid UTF-8 and24 successive append roots. Size tests compare actual immutable bytes written to full logical rewrite bytes; this is a synthetic disk-write measurement, not phone latency or a long-duration operating claim. A new Android instrumentation migration case is checked in but deliberately deferred with APK-based gates.

Important remaining limits: the Dart/native bridge still serializes and validates the complete logical book. Existing64MiB native logical cap,16MiB portable backup cap, per-archive8MiB/count bounds and non-Android preference storage remain. A referenced corrupt chunk fails whole-ledger read; financial-record-aware archive separation, streaming backup/export, incremental validation, recovery from verified backups and capacity-pressure owned-close acceptance still require work. Orphan staging chunks are retained rather than risking loss of user evidence; disk monitoring and safe verified compaction remain open. This implementation reduces physical rewrite amplification and provides immutable physical history; it does not close full work item3 or certify indefinite storage.

No source test APK/release packaging is requested by this batch. Direct JVM compilation/tests remain enabled.
