## ماذا أثبتت الاختبارات

- على اتصالين بقاعدة واحدة، عامل واحد يجلب الرمز المشترك ثم يحفظ مشاهدات مستقلة للحسابات؛ انتهاء lease يسمح بالاستئناف، والعامل السابق لا ينشر نتائج متأخرة بعد استيلاء آخر.
- إعادة تشغيل عملية Python مع نفس SQLite تحفظ حالة الحساب وميزانية الاتصال وحالة الرفض. مصادقة401/403 و429 والمهلة لا تُمحى بتغيير كائن الموصل أو العملية. الانقطاع الاصطناعي لا يولد أمرًا أو تعبئة أو ربحًا أو وقف خسارة من سعر مفقود.
- عند تعطيل الحساب أثناء الطلب لا يُكتب تحليل بإعداد سابق. استراتيجيات الحسابات منفصلة. أحداث القراءة/التحكم والأصل المرجعي لا تعبر الحسابات؛ تعديل/حذف الأحداث الأصيلة مرفوض من SQLite وPostgreSQL.
- الشموع تستخدم وقت الإغلاق، وترفض الحالات المستقبلية والقديمة/المتقطعة وغير المكتملة؛ replay يعتمد الأصل المحفوظ ووقت تسجيله، دون تقرير backtest سببي بأثر رجعي.
- اختبارات الحاويات **أوقفت API بالفعل** وبقي نبض collector يتحرك. ثم أُعيد تشغيل collector فظهر مالك عملية جديد من DB. ثم أُوقفت PostgreSQL فعليًا ففشل healthcheck، وأُعيدت فاستأنف العامل النبض. لم يتصل collector بالمزود خلال هذه الاختبارات.
- الاستعادة الحقيقية إلى قاعدة جديدة احتفظت بالدفاتر السابقة وبـruntime config/inbox/ack/cache link/request budget/backoff ورفض تعديل الأحداث بعد الاستعادة. المصدر وهدف الاستعادة fixture محليان فقط.

## حدود القبول والأمان

**غير منفذ:** اتصال حساب Alpaca، قطع إنترنت مزود فعلي، اختبار اشتراك الحساب المشترك، OPRA، تنفيذ خيارات بسعر سوق فعلي، هاتف جديد/Flutter جديد، خادم دائم أو soak test متعدد الجلسات، Push، penetration test، نظام متعدد المستخدمين مستقل الصلاحيات، تشفير/نقل backups خارج الخادم، load test وfailover إلى خادم آخر.

لا يُسجل هذا القبول كتشغيل24/7. Compose healthcheck يثبت حياة العامل فقط حتى عندما يكون `DISABLED`. انقطاع السوق اختُبر باستجابات نقل اصطناعية، وانقطاع قاعدة البيانات اختُبر فعليًا داخل Docker. هذه أدلة مختلفة ولا تُخلط.

لا منفذ تداول خارجي في الموصل: fixed-host HTTPS GET data allowlist، ولا Alpaca SDK/POST orders أو IBKR؛ مفاتيح Alpaca ملف صريح في collector فقط بعد sentinel موافقة منفصل. المصادقة الحالية توكن operator واحد، ومسارات الحسابات ليست تفويضًا بين ملاك مختلفين. أصل السجل محمي بـtrigger وdigest داخل حدود صلاحيات DB؛ مدير DB قادر على تعطيل triggers، فلا ندعي مقاومة مدير خبيث أو تخزين WORM.

حد الأرشيف1000/64MiB يوقف الحساب، ولا تُمسح سجلات لحل الامتلاء. هذا **نقص تشغيل دائم** مذكور صراحة في [دليل الجاهزية والتكلفة والربط](AUTONOMOUS_MARKET_RUNTIME_V1.md). الإشعارات API inbox فقط؛ موت الخادم لا يستطيع إرسال إشعار من داخله ويحتاج مراقبًا خارجيًا.
