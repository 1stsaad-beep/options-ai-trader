# Independent operational health exporter — batch68

A separate GET-only process exposes `/oat/v1/health` using a dedicated read-only probe token, not the owner API token. It has no account/control/order route, provider transport, Repository initialization, migrations or outgoing IO. It reads only an existing database through the existing database-enforced read-only connection, with bounded SQL/lock timeouts. Components and provider access diagnostics come from one consistent snapshot without taking the application writer/advisory lock. Each operational payload is bounded to4096 characters before JSON decoding.

The response separates database readability; worker/watchdog/delivery heartbeat freshness and state; sanitized worker diagnostics; and whether provider auth/backoff state is verified. Fresh DISABLED/SESSION_CLOSED/AUTH_BLOCKED states remain explicit; liveness never implies trading readiness or successful notification. Stale/future/invalid heartbeats become unavailable. A database/locked-schema/read failure returns503 and UNKNOWN component health, never a fabricated current worker state. Provider budget corruption becomes unverified. No account identifier, position, balance, owner identifier, URL, token, raw payload or driver error is exported.

Every authorized request requires one32-hex `X-OAT-Probe` nonce and receives it back with server time and no-store headers. A remote monitor can reject cached/late/mismatched responses. Authentication precedes database reads; duplicate auth/nonce headers, missing nonce and queries are rejected. There are no public docs or trading routes. Transport authentication does not cryptographically attest a compromised origin host.

The CLI `python -m app.health_exporter` is disabled unless `OAT_HEALTH_EXPORT_APPROVAL=read_only_approved`, paper mode and Live=false. It reads exactly `OAT_HEALTH_TOKEN_FILE`, a private regular no-symlink JSON file containing only token, plus explicit DATABASE_URL. It never reads OPTIONS_API_TOKEN or broker keys. Serving binds127.0.0.1:8082 with access logs disabled. An independently authorized TLS reverse proxy/network deployment remains required; none was created. `--check` verifies database readability only and cannot create a missing database. Exporter success is not proof of public reachability, continuous operation or outside-host outage detection.

16 new isolated tests cover readonly enforcement even if projection code attempts a write; absent database/no creation; coherent states; stale/future/blocked/disabled states; corrupted/oversized payloads; separate auth and nonce; no write/owner routes; private token loading; and disabled startup. The existing PostgreSQL gate adds3 checks for no writer/advisory lock, database-enforced readonly access and no changes to accounts/events/leases/provider state/alerts/receipts. Those three shared checks pass on disposable SQLite locally; PostgreSQL source CI is pending. Full local JUnit confirms1746 passed with zero failures/errors/skips, including16 new exporter cases. No external call, provider, actual token, deployment, financial order or APK.

An outside-host polling process, its own durable outage events and delivery integration remain the next programming step. This exporter alone does not claim to detect its own host loss. Database-connect DNS follows the existing read-only probe implementation; SQL timeouts are not an absolute network deadline. The outside monitor must bound the entire HTTPS probe and report missing/late exporter replies as unavailable, without labeling an unobserved component as healthy.
